What UDS is and what I did

ASU's Universal Design System (UDS) was made for websites, in Bootstrap. Our team at ASU's Learning Engineering Institute builds AI tools for teachers and students. Those are apps, not websites, and every AI coding tool writes Tailwind.

So I extended UDS into a Tailwind-based system. I didn't start from zero. I kept ASU's brand and grew the system into something apps can use.

  • 70+production-ready components
  • FigmaVariables and Auto Layout
  • WCAG 2.2on desktop and mobile
  • Writtenusage guidelines

I also introduced version control in Figma across LEI projects, with branching and naming rules. The system is used in ReQuesta and the AIX Framework app.

Process and decisions

The case study has the timeline and the token structure. Here are the decisions behind it, in short.

Test before committing

Before picking Tailwind, I prompted AI tools and generated real component code with MCP. The output was Tailwind every time. That settled it.

Stretch, don't detach

The old components were rigid. When a requirement changed, I had to detach the component and rebuild it. Every component is now built with Auto Layout and properties, so it stretches to fit instead of breaking.

Variables, not hand-typed values

Colors, spacing and type live in Figma Variables. Components only point at them, so they switch to dark mode without changes, and a value is changed in one place.

Names developers already know

I asked a developer how the class names should feel before writing any. They knew Bootstrap, so we kept it short: btn btn-brand, with Tailwind underneath.

Every state drawn

Each component shows default, hover, focus and disabled. Focus is where accessibility usually breaks, so it is never left for later.

Keeping the files in order

Before I set it up, LEI had no agreed way to track design changes. Several people worked in the same files.

I introduced version control in Figma as a way of working across LEI projects, not as a one-product fix. I set the branching, versioning and naming rules, so:

  • design changes stay tracked,
  • earlier releases stay intact and usable while new design ships,
  • components stay reusable when several people work in the same files.

On ReQuesta, which is built on the system, that looks like a Design Log with numbered versions (v1.0.1 on Jul 8, v2.0.0 on Aug 19, v2.0.1 on Aug 26, 2026) and one naming grammar for components: type_property_descriptor.

This is the part people skip. Building a system is common. Keeping it in one piece while several projects use it at once is the harder half.

Accessibility: WCAG 2.2

I kept every product WCAG 2.2 compliant on desktop and mobile. In the system that means keyboard navigation, visible focus indicators and screen-reader labels, built into the components.

The brand colors need care. ASU gold (#FFC627) on white is 1.57:1, far below the 4.5:1 that text needs. So gold is never text on a light background.

How the guidelines are written

Usage notes and class names sit right next to each component in Figma. Every component goes the same way: definition, states, annotation, handoff.

When I write a guideline, I follow a few rules:

  • Plain words. Short lines a new designer or developer can read in a minute.
  • Rules you can check. "Text is at least 4.5:1", not "use good contrast".
  • Say when not to use it. Most mistakes are the right component in the wrong place.
  • Show the code name. The class a developer types sits next to the drawing.

Three short examples follow. They show the format. They are written for this page from what is already public.

The team's real guideline text and Figma library stay private.
Example write-up

Button

Use it for
An action the person takes now: save, send, continue.
Variants and states
Solid, Ghost and Outline. Brand, Secondary, Success and Danger. Default, hover, focus and disabled.
Do
Use one Solid Brand button for the main action on a screen. Write the label as the action: "Save draft", not "Click here".
Don't
Use Danger for anything other than deleting or actions that can't be undone. Put gold text on a light background.
Accessibility
A focus ring you can see, never hidden behind a sticky header (WCAG 2.2, 2.4.11). Works with Enter and Space.
Code
<button class="btn btn-brand">Save draft</button>
Example write-up

Alert

Use it for
A message about the page or a task: it worked, something to know, or something went wrong.
Variants
Success, Info and Danger.
Do
Say what happened and what to do next, in one or two lines.
Don't
Let color carry the meaning on its own. Every alert has an icon and words too.
Accessibility
Screen readers announce it when it appears. Only errors interrupt; other alerts wait their turn.
Example write-up

Text input

Use it for
One line of text: a name, an email, a search.
Do
Always show a label above the field. Say how to fix an error, not only that there is one.
Don't
Use the placeholder as the label. It disappears as soon as someone types.
Accessibility
The label and error message are tied to the field, so screen readers read them. The error state uses words and an icon, not only a red border. Click targets are at least 24 by 24 pixels (WCAG 2.2, 2.5.8).
Code
<input class="form-input" id="email" type="email">

Figma to code: a team project

The Figma-to-code pipeline is team work. It was led by Nishad Patne, senior designer at LEI, with three developers. My part was ReQuesta's components and UX copy.

The pipeline does three things:

  1. Sync. The Figma API moves design tokens and UX copy between Figma and code, both ways, so each value has one source.
  2. Map. Code Connect links each Figma component to its real code, so AI tools find a component by what it is, not by how it looks.
  3. Audit. An MCP-driven pass flags detached copies, hardcoded values, and token, type, spacing and state mismatches.

For my part, I turned ReQuesta's UX copy into Figma Variables that developers pull straight into the code. The copy stays the same in design and code instead of being retyped and drifting.

Making a system readable by AI

UDS started from one fact: AI tools write Tailwind, so the system should too. Code Connect took it further by telling AI tools which component is which.

I wanted to know what actually stops an AI from misusing a component. So I made a small follow-on experiment, the Proposal kit: a tiny design system for one solar proposal summary, with made-up data. I designed it and directed Claude Code, which wrote the code.

The rules inside the components mattered more than the docs.

Twenty fresh Claude Code runs built the same page, half with the AI docs and half without. The four costly mistakes I designed against never happened, with or without docs. Every run read the components, and the required props did the work.

One slip still got through: a divider placed inside a definition list. It looked fine on screen and broke the markup for screen readers. It showed up in 5 of 10 runs without the docs and 1 of 10 with them. The docs never mention it, and these are small samples, so that is not proof the docs helped.

What I'd bring back to a system like UDS: put the rule in the component where you can, keep the docs short, and test with agents that have never seen the system.
